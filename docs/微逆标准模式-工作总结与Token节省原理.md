**工作总结 · Token 节省原理 · v1→v2 进步对比（详细版）**

> 2026-08-24 · 配套 Word 版：`微逆标准模式-工作总结与Token节省原理.docx`

---

## 一、项目背景与目标

### 1.1 背景：大模型推理的行为特征

DeepSeek-V4 系列是带可见思维链（Chain-of-Thought）的推理模型：模型在给出正式回答前，会先输出一段或多段 reasoning 块。这些推理块既可能高效（直接、集体、决定性），也可能低效（口语化、探索式、自我怀疑）。默认行为下，模型倾向于以第一人称单数起手：

- **"Let me check..."** —— 把"行动"推迟为"打算"，经常伴随多轮空转探测；
- **"I think I should..." / "I'm not sure..."** —— 自我怀疑式推理，占输出 Token 却不产生执行价值；
- **"Interesting! / Excellent!"** —— 感叹式叙述，无信息量。

这类"口语化思维"有三个代价：(1) 输出 Token 浪费；(2) 推理发散导致步数增加、工具调用增多；(3) 在长会话中，随着上下文增长，系统提示词头部的约束指令因注意力稀释（recency bias）而逐渐失效，模型退化为默认的冗思模式。

### 1.2 项目目标

- **核心目标一**：强制思维链以 `we need ...` 起手，将推理锁定为"集体、决定性、Token 精益"的高效执行框架；
- **核心目标二**：极致减少上下文占用与 Token 消耗，最大化供应商 KV Cache 命中率；
- **实现要求**：冷启动锚定（首轮只暴露 2 工具）+ 动态晋升（首次工具调用后解锁完整目录）+ 上下文瘦身（结果裁剪落盘、80% 压力压缩）+ 前缀稳定（KV Cache 友好）。

### 1.3 载体

本方案落地为 DeepSeek Harness（DSH）的一个 Agent Preset：**微逆标准模式（micro-inversion-standard）**。DSH 的 Agent 预设机制提供了一组真实可用的拦截点（`system-prompt/assemble`、`agent/pre-step`、`tools/post-execute`、`agent/request` 等），使上述目标可以工程化实现并通过会话日志逐条验证。

## 二、总体架构

### 2.1 预设组成（文件清单）

| 文件 | 作用 |
| --- | --- |
| `agent.cordis.yml` | 预设组合：19 行（persona、tool-bootstrap、持久 shell、标准工具目录、context-slimmer、anchor-sustainer 等） |
| `tool-bootstrap.mjs` | 阶段一锚定 + 动态晋升状态机 + L1 认知 persona 构建 |
| `context-slimmer.mjs` | `tools/post-execute` 结果裁剪+落盘；`agent/pre-step` 80% 压力中段压缩 |

| `preset.yml` / `TEST.md` / `NOTICE.md` | 元数据、验收清单、说明文档 |

### 2.2 两阶段总览

- **阶段一（冷启动）**：模型只看到 2 个工具（持久 shell + `str_replace_editor`）、只看到 persona 提示词、无运行时上下文、输出上限 1024 Token；
- **阶段二（晋升后）**：完整标准目录（39 个工具）+ 全部提示词与上下文恢复 + v2 全局锚持续生效。

### 2.3 单步请求处理链

```
用户消息 → inbox 认领 → agent/pre-step（阶段一消息过滤 / L2 近场锚注入 / 漂移检测与早期裁剪）
  → system-prompt/assemble（阶段一 sections 过滤 / 晋升后 L1 persona 换装）
  → 模型推理 → 工具调用 → tools/post-execute（L3 结果锚 + 结果裁剪落盘）
  → 下一 step（循环，直到回合结束）
```

## 三、核心机制详解

### 3.1 冷启动锚定（阶段一）

#### 为什么只暴露 2 个工具

工具目录是模型"选择熵"的来源：工具越多，模型越倾向于先用工具试探，推理越发散。只暴露 `持久 shell + str_replace_editor` 迫使模型首轮就进入"执行"而非"探索"心态，同时让首轮请求的输入面极小、输出预算集中。

#### 1024 输出上限："we need 触发窗口"

阶段一把输出预算压到 1024 Token（社区观测的 "We need" 触发窗口）。短预算下模型无法展开冗长探索，只能以最短的推理块直接给出 `we need ...` 并执行。晋升后该上限立即剥离，避免焊死在后续请求。

#### 提示词面过滤

`system-prompt/assemble` 钩子把 sections 过滤到只剩 persona，清空 contexts（无 sandbox/approval 快照），`agent/pre-step` 只放行 user/goal 两类消息来源，杜绝注入噪音。

### 3.2 动态晋升

首个持久 `tool/call` 或首次实质性回复（`assistant/message`）触发晋升：完整工具目录解锁、全部 sections 与运行时上下文恢复、工作目录注入。晋升在 step/turn 边界判定，绝不在工具执行中切换。压缩（compaction）会重写整个模型可见面，因此 `compaction/end` 后会话回落受控阶段（bootstrap 双工具 + 可选核心工具集），直到出现新的晋升信号。

### 3.3 上下文瘦身（context-slimmer）

#### 工具结果裁剪 + 落盘（tools/post-execute）

成功工具结果文本超过 8192 字符时：先全文落盘到会话级 spill 文件（`%TEMP%\dsh-spill-*/session-<hash>/<hex>-<tool>-result.txt`，0600 权限），再把模型可见内容替换为 **头 4096 + 恒定标记 + 尾 1024**，标记中给出真实路径与字节数。实测：pwsh 长输出 16244 字节 → 模型上下文只保留约 5120 字符。错误结果、嵌套子调用、含非文本块的结果跳过；落盘失败仅降级，绝不把成功调用变错误。

#### 80% 压力中段压缩（agent/pre-step）

`tokenMeter` 测得当前压力达到路由模型窗口 80% 时，把请求面中段消息整体替换为一条恒定标记，保留头 4096 / 尾 1024 字符；持久日志保留全文，`/compact` 负责持久摘要。与 compaction-basic 在同一 0.8 边界协同，互不冲突。

### 3.4 v2 全局运行态（anchor-sustainer）

#### L1 认知换装

晋升时把阶段一极简 persona 整体替换为"集体执行单元"身份（collective execution unit），包含：显式 CoT 语法（每个推理块必须以 `we need` 起手）、**FORBIDDEN openers 黑名单**（let me / I'll / I think... 等）、转场规则（工具结果后下一块仍以 `we need` 起手）、自检条款（违规即重写）、抗漂移声明（长会话中规则更重要）。身份层的行为惯性比语法禁令更持久。

#### L2 近场锚

每次模型请求前，在 messages 数组**尾部**追加一条恒定微指令（"Open this next reasoning block with: we need"）。原理：注意力对近生成点的 token 最强，头部指令在长上下文里权重衰减，而尾部锚始终出现在注意力最强处。文本恒定 → 前缀 KV Cache 不受影响；每步恰好一条、幂等。

#### L3 结果锚

每个工具结果通过 `additionalContexts`（harness 原生"结果 → 下一请求"通道）挂载恒定接续指令（"Result received. Next reasoning block opens with: we need"），防止"拿到结果 → 规划下一步"这一高发转场点破功。不修改结果文本、不污染持久日志，成本约 30 Token/次。

#### D 漂移检测闭环

增量扫描会话日志中每个推理块的起手词（三分类：conform / soft / violation），按会话维护计数，分级升级：

| 级别 | 触发条件 | 动作 |
| --- | --- | --- |
| 0（基线） | 连续违规 < 2 | 基线锚文案 |
| 1（强化） | 连续违规 ≥ 2 或累计 ≥ 3 | 升级锚文案 + 注入重述消息（引述违规原文） |
| 2（再锚定） | 累计 ≥ 6 或近 20 块漂移率 ≥ 30% | 早期中段裁剪（压力 ≥ 40% 即触发）+ 收紧 maxTokens 至 2048 |

连续 3 个合规块自动降级，防止矫枉过正。检测在本地日志上增量扫描，零 Token 成本。

## 四、Token 节省原理（核心）

### 4.1 输出侧：推理长度控制

口语化探索式推理消耗大量输出 Token 却不产生执行价值。本方案从三个层面压缩：

- **起手式约束**：`we need ...` 要求先陈述单一下一步，天然压缩推理结构；
- **阶段一 1024 上限**：把首轮推理压到最短；
- **v2 漂移收紧**：检测到违规漂移时把 maxTokens 压到 2048，挤压冗思，恢复后自动解除。

实测：同一"检查电脑整体环境"任务，v1 需要 13 个推理步，v2 只需 4 步——推理 Token 总量大幅下降。

### 4.2 输入侧：结果裁剪 + 落盘

工具大输出（几十 KB）若原样进入上下文，会迅速耗尽窗口。裁剪策略只保留 头 4096 + 尾 1024（约 5KB），全文落盘按需读取——模型上下文里永远只有摘要，全文只在不必要时才被读取。实测：16244 字节 → 5120 字符，节省约 70% 的该结果占用。

### 4.3 上下文侧：压力中段压缩

上下文压力达到窗口 80% 时，把注意力价值最低的中段消息替换为恒定标记，头尾保留。相比整段丢弃或摘要重写，中段替换保留了任务关键的头（系统提示词）与尾（近期消息），等效延长会话可用窗口，推迟真正的 compaction。

### 4.4 缓存侧：KV Cache 命中最大化

供应商对前缀做 KV Cache：请求前缀不变则命中缓存，输入费用按命中价计。本方案的缓存策略：

- 系统提示词、工具目录、头部消息在阶段一/阶段二各自**字节级稳定**，跨步不变；
- 锚文本恒定（L2/L3 用固定字符串），注入不改变既有前缀；
- 新消息与工具结果只追加在尾部；
- 裁剪只替换连续中段（一个结果节点原文，或一段中段消息），头尾逐字不动。

效果：除首次请求外，绝大多数请求命中缓存前缀，输入费用显著下降（usage 中的 `cacheReadTokens` 字段可观测）。

### 4.5 Token 账本（每步新增成本）

| 项 | 成本 | 说明 |
| --- | --- | --- |
| L1 认知换装 | 一次性 | 仅晋升时发生一次 |
| L2 近场锚 | ≈30 Token/步 | 恒定文本，每步一条 |
| L3 结果锚 | ≈30 Token/次工具调用 | additionalContexts 挂载 |
| D 漂移检测 | 0 Token | 纯本地日志扫描 |
| 结果裁剪 | 节省 | 大输出 5KB 摘要替代全文 |
| 中段压缩 | 节省 | 80% 压力时丢弃中段 |
| KV Cache 命中 | 节省 | 未变前缀按命中价计费 |

**结论**：每步新增 ≈60 Token 的锚定开销，换来推理冗思、重复前缀输入、大输出占用的多重节省，净收益为正。

## 五、优点总结

- **执行更果断高效**：实测同任务 13 步 → 4 步，工具调用更少、收敛更快。
- **上下文 / Token 更省**：结果裁剪 + 压力压缩 + 缓存命中三管齐下。
- **长会话稳定**：v1 实测 2/13 推理块以 `we need` 起手（15%），v2 实测 4/4（100%）、零违规——注意力稀释问题被三层锚 + 检测闭环解决。
- **可观测、可调参**：每个锚与检测事件都落在会话日志里；阈值全部可配置（裁剪阈值、压力比率、输出上限、升级门槛等）。
- **工程健壮**：组合漂移降级、spill 失败降级、未知窗口跳过、模块缓存版本化——绝不锁死会话。
- **可验证**：所有行为都能从会话日志（request/header、assistant/message 推理块、user/message 锚事件）逐条取证。

## 八、工程经验与踩坑记录

- **Node ESM 模块缓存**：预设本地 `.mjs` 插件行名必须带 `?v=N` 版本号，否则修改插件后重挂载仍命中旧模块缓存（import 按 URL 缓存）。
- **spill locator**：spillStore 返回的 `ref.locator` 才是文件真实路径，`ref.retrievalHint` 是固定文案（"Use read with offset/limit..."），不能当路径用。
- **session/event 陷阱**：agent 平面 preset 中 `session/event` 事件被 dsh-scope 过滤、永不触发，漂移检测必须用 `session.events` 数组增量扫描。
- **测试提示词陷阱**：要求模型"原样复述完整输出"会诱发逐块 read 死循环（3000 行逐 60 行读数百次），测试应改为报告裁剪标记与落盘路径。
- **上游截断**：harness 对长输出截断在约 16KB，且 `<response clipped>` 提示会内联拼入结果流，成为 spill 内容的一部分。
- **旧会话绑定旧组合**：已存在的会话绑定创建时的 standing mount，v2 改动只对新会话生效。

## 十、关键问题修正（v3 review）

> 针对评审提出的四项关键问题，逐条核实并修正如下：

### 10.1 "we need 只是风格代理指标，缺对照与真实 usage 数据"

**承认**：早期文档的"省 Token / 质量提升"结论主要基于单一任务的步数对比，没有
`standard` 基线、没有能力题本、没有真实 usage 数据。修正：

- 新增 **A/B 基准脚本**：同一任务题本（环境检查 / 求和 / 文件往返）分别跑
  `standard` 与 `micro-inversion-standard`，从会话日志提取真实
  `inputTokens / outputTokens / cacheReadTokens / reasoningTokens`、步数、
  工具调用数与能力校验（见 §11 实测表）；
- **锚定开销如实入账**：L2 ≈30 Token/步 + L3 ≈30 Token/次工具调用，文档不再
  宣称"净节省"而未给数据——是否净节省以实测为准；
- 步数对比的混杂因素（记忆基线复用）已注明。

### 10.2 中段裁剪不语义摘要，可能删除需求/授权/失败记录

**修正**：`context-slimmer` 的 `agent/pre-step` 裁剪改为**保护性裁剪**：

- **永不被裁**：真实用户消息（需求/验收条件）、审批记录（approval）、目标轮次
  （goal）、模型分析（assistant 角色）——见 `PROTECTED_KINDS` 与 `splitTrimable`；
- 只裁剪中段的**可丢弃内容**：工具结果、运行时快照、锚、注入提醒；
- 标记**枚举被裁内容**（种类计数 + 工具 callId），并提示模型"若其中有失败记录或
  任务所需，可重跑/重读；durable log 保留全文，/compact 生成持久摘要"。

### 10.3 实现错误：meter/llm 缺失或窗口未知时在 0% 压力下直接裁剪

**确认并修复（真实 bug）**：原 `agent/pre-step` 压力门控在 `meter/llm 缺失`、
`路由未知`、`窗口未知` 三种情况下不 return、直接落到 `splitSurface` 裁剪。
已重构为**默认跳过**：`over` 初始为 `false`，只有显式测得压力 ≥ 阈值才裁剪；
任何未知路径都原样放行。单测覆盖四种路径（缺失 / 窗口未知 / 压力不足 / 压力达标）。

### 10.4 漂移触发破坏性动作，措辞合规优先于任务完整性

**修正**：`anchor-sustainer` 的漂移检测改为**纯软强化**：

- 升级动作只剩：强化锚文案 + 重述消息（引述违规原文）；
- **删除**漂移触发早期裁剪与 maxTokens 2048 收紧（`agent/request` 钩子移除）；
- 分类只统计每条消息的**首个推理块**（frame-setter），延续块不升级；
- 上下文管理完全交给 `context-slimmer`（显式压力门控 + 保护性裁剪）。

'we need ...' line, call a tool immediately"）。重跑验证：无卡死、5/5 完整、16/16
合规。注：阶段一前缀跨会话命中 KV 缓存（cacheRead 1152 vs input 17），缓存机制正常。

1. **输出/推理量级缩减可复现**：v2/v3 环境检查推理 tokens 362~2,599 vs standard
   21,843（约 8~60×），输出 2,017~6,081 vs 27,751（约 4~14×）；求和任务输入减少
   3 倍。锚定开销（≈30 tokens/条）相对节省可忽略。
2. **完整性权衡已缓解**：早期 v2 单次会话漏报 Build 号（4/5）；补充完整性条款后

   方向性参考。
4. **cacheRead 不做结论**：请求次数与前缀长度不同（v2 请求更少、前缀更短），
   原始数值不可直接对比，仅如实列出。

## 十二、彻底对比（受控 A/B：5 题 × 2 预设，同一时间窗）

> 2026-08-24 实测：同题本（环境检查/插件描述/文件往返/五项事实/求和公式）在
> `standard` 与 `micro-inversion-standard` 各跑一次，从会话日志提取真实 usage。

### 答案质量（存在性 + 正确性核验）

| 题本 | standard | micro-inversion |
| --- | --- | --- |
| 环境检查（5 项事实） | 4/5 | **5/5** |
| 插件描述（5 项事实） | 5/5 | 5/5 |
| 文件往返（3 字段） | 3/3 | 3/3 |
| 五项事实查询 | 5/5 | 5/5 |
| 求和+公式 | 2/2 | 2/2 |
| **合计** | **19/20** | **20/20** |

结论：答案质量**持平**（一跑内 1 分差异属噪声；standard 也会漏报——本次 env 漏一项）。
微逆**没有以质量为代价**。

### Token 实测（合计，5 题）

| 指标 | standard | micro-inversion | 差异 |
| --- | --- | --- | --- |
| 输出 tokens | 53,336 | **14,533** | **−73%** |
| 其中推理 tokens | 42,021 | **6,033** | **−86%** |
| 输入 tokens | 63,025 | 49,105 | −22%（受跨会话缓存污染，仅供参考） |
| 锚定开销 | 0 | ≈1,560（52 条锚） | 相对节省可忽略 |

按题看：env −79%、plugins −29%、multifact −46%、sum −47%；**file 任务 micro 反而多
37% 输出**（琐碎任务上锚+persona 略增开销）——节约主要来自抑制冗思，对简单任务
不适用。

### 思考质量

| 指标 | standard | micro-inversion |
| --- | --- | --- |
| "let me" 类违规起手 | 1 次（plugins 任务） | **0 次** |
| "we need" 起手率 | 0%（无此约束） | 14/22 ≈ 64%（其余为合规软起手） |
| 推理冗长度 | 42,021 tokens | 6,033 tokens |

诚实说明：we-need 是**激励不是保证**——本窗实测 ~64% 起手合规、零违规；L2/L3 锚
持续推高但无法强制 100%。

### 各自优势

- **standard**：不干预模型风格，适合开放式探索/长篇分析；无起手约束；实现零成本。
- **micro-inversion**：输出/推理 token 明显节约（−73%/−86%）；零 "let me" 漂移；
  答案质量持平（20/20）；代价：~60 tokens/步锚开销、we-need 合规率非 100%、阶段一
  卡死风险（防复述条款已缓解）。

### 边界

单次采样、同任务方差大（env 步数 4↔10↔16）；input/cacheRead 受跨会话 KV 缓存
污染不可直接对比；质量"持平"需更大样本确认。此表替代 §11 的早期单任务数字。

### 真实编码任务反例（peak-valley-reminder 插件开发，2026-08-24）

> 同一任务在 micro-inversion 与 standard 各跑一遍：11 回合 / 27 步 / ~169 次工具
> 调用（edit 62 / pwsh 39 / read 33），用户逐轮验证 UI 并迭代、最终卸载，两者均成功。

| 指标 | micro-inversion | standard |
| --- | --- | --- |
| 输出 tokens | 140,185 | 136,929（micro **+2%**） |
| 推理 tokens | 72,147 | 70,462（+2%） |
| 计费输入 tokens | 636,217 | 423,782（**+50%**） |
| we-need 起手率 | 7/101 ≈ 7% | 0%（无约束） |
| let-me 违规 | 0 | 0 |
| 工具轨迹 | edit 62/pwsh 39/read 33 | edit 62/pwsh 37/read 31（几乎相同） |

**结论（重要边界）**：微逆的 token 节约**只对推理密集型任务显著**（§12 电池
−73%/−86%）；对**工具执行密集型**的编码任务不省反而略增——该任务绝大部分成本是
工具执行而非推理，可抑制的冗思本来就少，锚 + 更长 persona 的固定开销变成纯成本
（锚随每步持久化、推高计费输入）。we-need 起手强化在工具密集场景效果有限（多数
推理块是"刚读到结果"的观察续写），但**防 let-me 漂移稳定为 0 违规**，且答案质量
与 standard 持平。选择预设时应按任务类型：分析/多事实任务用微逆省 token；纯工具
执行的长编码任务两者相当，微逆无优势。
